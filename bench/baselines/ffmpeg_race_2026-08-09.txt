FOUR DEFECTS IN THIS HARNESS, FOUND TODAY, AND EVERY ONE FLATTERED US
  1. Each decode wrote a 1.74 GB YUV -- ~73 GB of writes per run. That measures the
     DISK, and both decoders converge toward disk speed. Read 1.816x/1.644x. Fixed:
     both sides sink to NUL.
  2. `Start-Process -PassThru` returned a handle without query rights, so
     TotalProcessorTime read 0 -- silently becoming a 0.000x ratio and a
     divide-by-zero. Fixed: [System.Diagnostics.Process]::Start.
  3. Adding $p.Refresh() to "fix" (2) made it worse: Refresh on an exited process
     invalidates the counters, so every read became 0.
  4. ffmpeg ran MULTI-THREADED while our decoder was pinned by RUSTY_THREADS=1.
     TotalProcessorTime sums CPU across threads, so ffmpeg's cost was inflated 1.55x
     (8,688 vs 5,609 ms on the same stream) by pure thread overhead. The claim under
     test says "single core". Fixed: -threads 1.
  A set of independent errors that all push the same direction is itself evidence
  that the harness was being tuned toward a hoped-for answer. Recorded for that
  reason as much as for the fixes.

DID TODAY IMPROVE DECODE? NO, AND IT SHOULD NOT HAVE.
Today was encoder work (CABAC 8x8, defaults, gate audits) plus ONE decoder change:
the CAVLC 8x8 nnz correctness fix. That fix only touches CAVLC streams carrying the
8x8 transform. The cavlc tier here is --profile baseline, which cannot signal 8x8,
and main/high are CABAC. So no tier in this corpus exercises it.

Measured directly, old (3bf242d, 0.8.0) vs new (HEAD), same box, same streams,
ABBA x5, median of paired ratios:

    cavlc   new/old 1.177x        main   new/old 0.935x

A 25% spread, in opposite directions, from a change that can affect neither stream.
That is the box's known drift, not a codec effect -- and it bounds the resolution of
this instrument: it cannot see anything smaller than about 25% between builds.
